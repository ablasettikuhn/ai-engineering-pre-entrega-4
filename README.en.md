Thanks to the multilingual embeddings, questions can also be asked in English.

## The real-world application: an evidence search engine for a performance staff

**The problem.** A club's performance staff (strength and conditioning coaches, physiologists, rehab specialists) makes daily decisions about training load, fatigue and injury risk. The evidence lives in scientific papers written in English, while the questions come up in Spanish and in a hurry: *"Is the Hooper index more useful than HRV after a match?"*, *"How valid are 10 Hz GNSS units?"*.

Asking a general-purpose AI assistant does not solve the problem. It answers from its general knowledge, without showing which study each figure comes from, and it can "hallucinate": produce convincing figures or claims that no study supports. It also cannot tell which evidence is the strongest for a specific discipline, such as load monitoring in team sports. For a performance staff, a made-up figure about fatigue or injury risk can end in a bad decision about a player.

**The solution.** A search engine that answers **only from the library of papers chosen by the staff**, and returns the 5 most relevant passages with author, year, page and DOI so they can be verified. Optionally, Gemini writes an answer that cites those passages. If the library has no evidence on the question, the system answers "I don't know" instead of making something up.

**Built to grow.** Today the library holds 8 papers. Tomorrow it could hold hundreds, plus other kinds of documents: the club's internal protocols, medical reports or federation guidelines. That is why the data lives in a cloud index (Pinecone Serverless), which scales without changing the code, and each document type can go in its own namespace.

**Why the cloud and why hybrid:**

| Real need | How this repo addresses it |
|---|---|
| The library grows (8 papers today, hundreds tomorrow, plus other document types) | **Pinecone Serverless** index: scales without managing servers; each data type goes in its own **namespace** |
| Questions use acronyms and proper names (sRPE, HRV, HRR, GNSS, Foster, Hooper) | **BM25** finds the exact term, which an embedding can "dilute" |
| Questions are in Spanish and the papers in English | **Vector search** (Gemini, multilingual) understands the meaning in both languages |
| Sometimes only one topic matters | Each chunk carries **categories** in its metadata, which can be used as a filter (`--categoria frecuencia_cardiaca`) |
| Citations must be accurate | Each chunk stores its **original text, paper and page** in Pinecone: no extra database is needed |

**Relation to Pre-entrega 3.** Pre-entrega 3 was a local RAG (ChromaDB) with 3 papers and vector-only search. This deliverable takes the same domain to the cloud, expands the library to 8 papers, adds lexical search and measures retrieval quality with metrics.

## Architecture

```mermaid
flowchart LR
    A[fuentes.json<br/>8 CC BY papers] -->|descargar_papers.py| B[data/*.md<br/>text + page markers]
    B -->|ingesta.py<br/>700-token chunks| C[Gemini embeddings<br/>1536 dim]
    C -->|upsert| D[(Pinecone Serverless<br/>index papers-ciencias-deporte<br/>namespace papers-cientificos)]
    D -->|vector query| E[PineconeRetriever]
    D -->|list + fetch<br/>text from metadata| F[BM25Retriever]
    E --> G[EnsembleRetriever<br/>Reciprocal Rank Fusion]
    F --> G
    G --> H[RAGSystem.buscar<br/>Top-5]
    H --> I[consultar.py]
    H --> J[evaluate.py<br/>Precision@5 / Recall@5]
```

| File | Purpose |
|---|---|
| `config.py` | Single source of configuration (reads the `.env`). Validates chunking, weights and index name. |
| `descargar_papers.py` | Step 0: downloads the PDFs, extracts the text page by page and generates `data/<id>.md`. |
| `setup_pinecone.py` | Step 1: creates or checks the Serverless index and validates dimension and metric. |
| `ingesta.py` | Step 2: chunking, embeddings and upsert with metadata. Idempotent. |
| `rag_system.py` | Step 3: `PineconeRetriever`, `BM25Retriever`, `EnsembleRetriever` and the `RAGSystem` class. |
| `consultar.py` | Real use: question → Top-5 with paper and page (and `--responder` with Gemini). |
| `evaluate.py` | Step 4: metrics on the Golden Set in 3 modes (vector, BM25, hybrid). |
| `golden_set.json` | 5 questions with their expected document. |
| `preguntas_trampa.json` | 2 in-domain questions the library cannot answer (similarity-threshold check). |
| `resultados/` | Logs and reports generated by the scripts (evidence). |

## Schema of a Pinecone record

Each chunk is a record with an `id`, `values` (the 1536-dimension embedding) and the metadata below. The **original text** travels in the metadata, so a query returns everything needed to display and cite the passage without querying another database.

| Field | Type | Example | Purpose |
|---|---|---|---|
| `texto` | string | "The Apex units (10 and 18 Hz) were…" | Original chunk text (shown by queries and used by BM25) |
| `doc_id` | string | `beato-2018` | Identifies the paper (used by the evaluation) |
| `fuente` | string | `beato-2018.md` | Source file |
| `titulo`, `autores`, `anio`, `revista` | string / int | `2018` | Bibliographic citation (title, authors, year, journal) |
| `doi`, `url`, `licencia` | string | `10.3389/fphys.2018.01288` | Traceability and license |
| `categorias` | list of strings | `["validez_dispositivos", "carga_externa"]` | Topic filter (`$in`) |
| `pagina`, `pagina_fin` | int | `4`, `5` | Page where the chunk starts and ends |
| `chunk`, `tokens` | int | `7`, `684` | Position of the chunk in the paper and its size |

The `id` is deterministic (`beato-2018-c007`): running the ingestion again overwrites the same records instead of duplicating them, and a whole paper can be listed or deleted by prefix.

## Technical decisions

- **Gemini instead of OpenAI, with the dimension requested by the assignment.** `gemini-embedding-001` lets you choose the output dimension; **1536** is used, the same as `text-embedding-3-small`. The index is therefore exactly as the assignment suggests, and Gemini has a free tier.
- **Protection against dimension mismatch.** `setup_pinecone.py` compares the dimension and metric of the existing index with those of the model before uploading anything, and the ingestion checks the length of every vector again. If you change `EMBEDDINGS_DIM` to 768 while the 1536 index already exists, the script stops with a message explaining what to do.
- **Native Pinecone SDK.** The assignment allows either `PineconeVectorStore` or the native SDK. The native SDK (version 10) was chosen because `langchain-pinecone` requires `pinecone<8`, a version that uses an older API. `PineconeRetriever` (in `rag_system.py`) is a short LangChain retriever on top of `index.query()`, and it shows exactly what is being queried.
- **Namespace.** The papers live in the `papers-cientificos` namespace. If the club added, for example, its internal protocols, they would go in another namespace of the same index: each search only scans data of its own type, with less noise and more speed.
- **700-token chunks with a 100-token overlap.** This is the midpoint of the 500-800 range. A "Methods" or "Results" paragraph of a paper fits whole, with its context, without mixing several topics in the same vector. Size is measured in tokens (`from_tiktoken_encoder`), not characters.
- **Exact page for each chunk.** The splitter returns literal pieces of the text, so the ingestion finds the position of each chunk in the document and maps it to a page using the `<!-- pagina N -->` markers.
- **BM25 with a custom tokenizer.** BM25's default tokenizer only splits on whitespace. The one in this repo lowercases, removes accents, drops Spanish and English stop words and keeps compound terms (`session-RPE` → `session-rpe`, `session`, `rpe`). PDF extraction normalizes ligatures ("ﬁ" → "fi") so BM25 does not miss words.
- **The BM25 corpus is read from Pinecone.** `RAGSystem` lists the IDs in the namespace and fetches their metadata (`list` + `fetch`). BM25 and vector search see exactly the same chunks with the same IDs, and the `data/` folder is not needed for querying.
- **Fusion with `EnsembleRetriever`.** Each retriever contributes 10 candidates. The ensemble combines them with Reciprocal Rank Fusion (weights BM25 0.4 / vector 0.6) and `RAGSystem` returns the top 5. Vector search gets more weight because the questions are in Spanish and the papers in English. `id_key="chunk_id"` ensures that a chunk found by both retrievers counts once, adding up its scores. The weights can be changed in the `.env`.
- **Origin of each result.** Queries and the evaluation show whether each chunk was found by BM25, vector search or both. This makes it visible in practice what each one contributes.
- **Minimum similarity threshold.** BM25 always returns something (some word always matches), so the decision "the library has no evidence on this" is made with the cosine similarity of the closest chunk. If it falls below `UMBRAL_SIMILITUD`, `consultar.py` warns about it and `--responder` answers "No lo sé con los papers disponibles." ("I don't know with the available papers.") without calling Gemini, which could fill the gap with its own knowledge. The threshold is not set by eye: it is calibrated with the real and trap questions (see [Evaluation](#evaluation)).
- **Pinned versions.** `requirements.txt` pins every dependency with `==`, so anyone can reproduce the same environment used to obtain the results.
- **Free-tier quota.** The ingestion sends embeddings in batches of up to 25,000 tokens per minute and retries on a 429 error. The evaluation caches each question's embedding in memory so it is not computed twice.

## How to replicate the index

Tested on Windows with Command Prompt and Python 3.14 (compatible with Python 3.12 or later).

### 0. Requirements

- A **Pinecone** API key (free Starter plan): https://app.pinecone.io → *API Keys*.
- A **Gemini** API key (free tier): https://aistudio.google.com/apikey.

### 1. Clone and install

```
git clone https://github.com/ablasettikuhn/ai-engineering-pre-entrega-4.git pre-entrega-4
cd pre-entrega-4
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

### 2. Configure the keys

```
copy .env.example .env
notepad .env
```

Fill in `PINECONE_API_KEY` and `GOOGLE_API_KEY`. All other values already have working defaults.

### 3. Run the pipeline

| Command | What it does | How to verify |
|---|---|---|
| `python descargar_papers.py` | Downloads the PDFs and generates any missing `.md` files in `data/` (existing ones are skipped) | Ends with "Dataset: 8 de 8 papers listos en /data" (8 of 8 papers ready) |
| `python setup_pinecone.py` | Creates the Serverless index (AWS us-east-1, 1536 dim, cosine) or checks the existing one | "Índice creado y listo" (index created and ready) or "ya existe" (already exists) + index status |
| `python ingesta.py` | Chunking, embeddings and upsert into the namespace. Takes a few minutes because of quota pauses | Ends with "Ingesta completa: N vectores" (ingestion complete) and prints a sample record |
| `python ingesta.py` (again) | Detects that the namespace is up to date and does not re-index | "ya está al día … no se re-indexa" (up to date, not re-indexed). `resultados/log_ingesta.txt` keeps both runs |
| `python setup_pinecone.py` | Shows how many vectors are in the namespace | The number matches the ingestion |
| `python evaluate.py --actualizar-readme` | Computes the metrics, runs the trap-question check, saves the report and updates the table in the Spanish README | Prints Recall@5, Precision@5 and MRR, and the checks with PASA/FALLA (pass/fail). If the threshold check fails, the report suggests a value: set it as `UMBRAL_SIMILITUD` in the `.env` and run again |

### 4. Use the search engine

```
python consultar.py "¿Qué validez tienen las unidades GNSS de 10 Hz y 18 Hz?"
python consultar.py "¿Qué validez tienen las unidades GNSS de 10 Hz y 18 Hz?" --modo bm25
python consultar.py "¿Cómo cambia la HRV después de un partido?" --categoria frecuencia_cardiaca
python consultar.py "¿Cómo se calcula la carga con el método session-RPE?" --responder
python consultar.py "¿Qué dosis de cafeína mejora el rendimiento en sprints repetidos?" --responder
python consultar.py "How valid are 10 Hz GNSS units for measuring peak speed?"
python consultar.py
```

Add `--guardar` to any query to append its output to `resultados/ejemplo_consulta.txt` (evidence).

The caffeine question is a trap: the library does not answer it, so the system warns that there is not enough evidence and answers "I don't know". The English question shows that queries can also be asked in English. The last command opens interactive mode (type `salir` to exit). `--modo vectorial` and `--modo bm25` allow comparison with hybrid search, which is the default.

**To start from scratch:** `python ingesta.py --forzar` empties the namespace and re-indexes everything. If you change the embedding model or dimension, also use a different `INDEX_NAME`.

## Evaluation

### Golden Set

`golden_set.json` contains 5 questions in Spanish. For each one, the paper that answers it is known in advance. The questions combine the cases where each type of search is expected to help:

| ID | Question (summary) | Expected paper | Type |
|---|---|---|---|
| q1 | Calculating load with Foster's session-RPE | `haddad-2017` | acronym + proper name |
| q2 | Validity of 10 and 18 Hz GNSS units | `beato-2018` | technical term + figures |
| q3 | Hooper index vs. HRV after a match | `rabbani-2019` | proper name + acronym |
| q4 | Predicting injuries with GPS and machine learning | `rossi-2018` | conceptual |
| q5 | Heart rate measures to monitor training status | `buchheit-2014` (also relevant: `schneider-2018`) | conceptual, two relevant papers |

The 3 remaining papers (`torres-ronda-2022`, `gomez-carmona-2020` and, for q1-q4, `schneider-2018`) act as distractors: they cover nearby topics (tracking, accelerometry, heart rate) and could be confused with the expected paper.

### Metrics

- **Recall@5:** is the expected paper among the 5 retrieved chunks? 1 or 0 per question. With a single expected paper per question, it is equivalent to the hit rate.
- **Precision@5:** proportion of the 5 retrieved chunks that come from a relevant paper (the expected one or those listed in `documentos_relevantes`).
- **MRR (extra):** 1 / position of the first chunk from the expected paper. It rewards the correct paper appearing at the top.

`evaluate.py` computes the three metrics in the three modes (vector, BM25 and hybrid) to show what the combination contributes.

### Trap questions and similarity threshold

A good retriever must also recognize when the library does **not** have the answer. `preguntas_trampa.json` contains two in-domain questions that no paper answers:

| ID | Question (summary) | Why it is a trap |
|---|---|---|
| t1 | Caffeine dose (mg/kg) for repeated sprints | No paper studies caffeine; the LLM knows a figure from memory |
| t2 | Grams of protein per kilo for a soccer player | Nutrition: outside the library |

`evaluate.py` computes the maximum similarity of the 5 real questions and the 2 trap questions. The check **passes** if all real questions are at or above `UMBRAL_SIMILITUD` and the trap questions are below it. Otherwise, the report gives the midpoint between the lowest real similarity and the highest trap similarity as a suggested threshold. The threshold is calibrated with data, not set by eye.

### Interpretation of the results

- **Recall@5 = 1.00 in all three modes.** The 5 questions target papers with clearly different topics, so each search on its own already finds the correct paper. The benchmark confirms that the whole pipeline works end to end (ingestion, metadata, vector search, BM25 and fusion), but 5 questions are not enough to show a difference between the modes.
- **BM25 is slightly lower in Precision@5 (0.96).** One of its 25 chunks came from a non-relevant paper: BM25 only matches the words shared by the Spanish question and the English paper. Multilingual vector search did not make that mistake, and neither did hybrid mode.
- **What hybrid mode contributes.** In this golden set no retriever failed, so hybrid search equals vector search. Its value shows when one of the two fails and the other compensates. `resultados/ejemplo_consulta.txt` shows, for each chunk, whether it was found by BM25, vector search or both. The next step would be a more demanding golden set: questions phrased only with an acronym or a surname, or questions where two papers compete.
- **Similarity threshold.** Real questions scored between 0.760 and 0.833 maximum similarity, and trap questions between 0.614 and 0.645. The 0.70 threshold sits in the middle of that gap, with a margin of about 0.06 on each side. It is a small margin: a trap question closer to the library's topics could exceed it, so the threshold should be recalibrated as the library grows.

### Limitations

- **The threshold was calibrated with 7 questions.** It separates these cases well, but more real and trap questions would make the calibration more reliable.
- **5 questions is a small sample.** It is enough to compare modes and catch major errors, not to give a definitive quality figure.
- **Relevance is judged per paper.** A chunk counts as useful if it comes from the expected paper, even if that specific passage does not answer the question. It is a reasonable approximation for a small benchmark.
- **BM25 lives in memory.** It is rebuilt on every run from the Pinecone metadata. This works very well with hundreds or thousands of chunks. With millions, lexical search inside Pinecone itself (sparse vectors or full-text search) would be preferable, to avoid loading the whole corpus.
- **Language.** BM25 only matches the words shared by the Spanish question and the English paper (acronyms, names, technical terms). A future improvement would be to translate the question into English keywords before passing it to BM25.

## Glossary

### Acronyms and proper names in the papers

The papers use these terms as they are, in English. They are the kind of word BM25 finds exactly: if the question says "HRV" or "Hooper", BM25 looks for exactly that word in the chunks, even if the rest of the question is in Spanish.

| Term | Meaning | Main paper |
|---|---|---|
| **RPE** | *Rating of Perceived Exertion*: the athlete's subjective rating of effort, usually on Borg's CR-10 scale (0 to 10). | `haddad-2017` |
| **sRPE / session-RPE** | Internal load of a session: RPE × session duration in minutes. Expressed in arbitrary units (AU). Example: RPE 7 × 60 min = 420 AU. | `haddad-2017` |
| **Foster** | Carl Foster, exercise physiologist. He and his colleagues proposed the session-RPE method in the late 1990s, which is why it is called the "Foster method". | `haddad-2017` |
| **HR** | *Heart Rate*, in beats per minute. | `buchheit-2014`, `schneider-2018` |
| **HRV** | *Heart Rate Variability*: how much the time between consecutive heartbeats varies. Measured at rest, it reflects parasympathetic nervous system activity. A drop can indicate fatigue. | `buchheit-2014`, `rabbani-2019` |
| **HRR** | *Heart Rate Recovery*: how much heart rate drops in the first minutes after a submaximal effort. Faster recovery usually indicates better fitness. | `buchheit-2014` |
| **HRex** | *Exercise Heart Rate*: heart rate during standardized submaximal exercise, for example during the warm-up. | `buchheit-2014`, `schneider-2018` |
| **Hooper index** | Wellness questionnaire by Hooper and Mackinnon (1995). The athlete rates four items: sleep quality, stress, fatigue and muscle soreness. A higher total indicates poorer wellness. | `rabbani-2019` |
| **GNSS** | *Global Navigation Satellite System*: the general term for satellite positioning systems (GPS, GLONASS, Galileo, BeiDou). Player-worn devices use it to measure distances and speeds. | `beato-2018` |
| **GPS** | The US positioning system, one of the GNSS. In sport, "GPS" is commonly used for any satellite tracking device. | `rossi-2018`, `torres-ronda-2022` |
| **Hz (10 Hz, 18 Hz)** | The device's sampling rate: 10 Hz means 10 positions recorded per second. A higher rate improves accuracy in short actions, such as a sprint. | `beato-2018` |
| **Peak speed** | The maximum speed reached in an action or session. | `beato-2018` |
| **Accelerometry** | Measuring accelerations with the device's inertial sensors (usually placed between the shoulder blades). It quantifies jumps, impacts and changes of direction that GNSS does not capture well. | `gomez-carmona-2020` |
| **Machine learning** | Models that learn patterns from data. In `rossi-2018` they are used to predict injuries from load recorded with GPS. | `rossi-2018` |
